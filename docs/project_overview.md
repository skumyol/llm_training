# Structured Latent-State NPC Dialogue: System Overview

## Motivation

Standard LLM-based NPCs generate dialogue autoregressively from raw context, with no explicit reasoning about the social dynamics of the conversation. This means there is no reliable way to control *why* an NPC says what it says, to audit secret-keeping behaviour, or to guarantee stance consistency across turns. This project addresses that gap by building a model that first predicts a structured social latent state at every turn, then generates a response *conditioned* on that state.

---

## Part 1 — Data Generation Pipeline

Because no labelled dataset exists for this task, the full training corpus is synthetically generated using a teacher LLM (Qwen3-8B, run locally) following a deterministic 7-stage pipeline.

```
ScenarioBank → StateInit → EpisodePlanner → TurnGenerator → CounterfactualAugmenter
                                                    ↓
                                               Validator → Packager → Splitter
```

### Stage 1: Scenario Bank
YAML templates define the space of social situations: `secret_extraction`, `apology_repair`, `alliance_negotiation`, `rumor_confrontation`, `threat_escalation`, `trust_building`, `deception_detection`. Each template specifies the setting, stakes level, turn budget, required narrative events, and an NPC role pool. Weighted sampling during generation controls class balance.

### Stage 2: State Initialization
A rule-based function (`build_npc_profile`) constructs the NPC's *persistent state* W — role, goals, secrets, persona style, and an initial relational stance vector — from a lookup table keyed on `(role, stakes)`. This is intentionally not free-form LLM generation: deterministic construction prevents contradictory NPC personalities.

### Stage 3: Episode Planner
Before any dialogue is generated, a hidden **social arc** is planned: a phase schedule (`approach → probing → pressure → resolution`), required state-variable shifts at specific turns (e.g. `trust` must drop by turn 4), and a reveal ceiling (how much of the NPC's secret may be disclosed at most). The arc acts as a hard constraint on the generator.

### Stage 4: Turn Generator — the 10-step sequence
At every turn the teacher LLM runs a strict chain of structured prompts:

| Step | Output | Prompt |
|------|--------|--------|
| 1 | Scene context assembled | — |
| 2 | Player utterance x_t sampled or generated | `player_generation.txt` |
| 3 | **C_t** — dialogue act, tone, risk type | `label_C.txt` |
| 4–5 | **A_t / M_t** — NPC affect appraisal + player mental model | `label_A_M.txt` |
| 6–8 | **R_t / N_t / D_t** — relational stance update, norm pressures, response policy | `label_R_N_D.txt` |
| 9 | NPC response y_t conditioned on D_t | `response_generation.txt` |
| 10 | Validate and persist | — |

Each JSON label is extracted from the LLM output against a fixed vocabulary (`LABEL_SCHEMA`). Retry logic with temperature escalation handles malformed or repetitive outputs. The result is one richly annotated turn record per step.

### Stage 5: Counterfactual Augmenter
For every validated episode, 2–3 variants are generated by flipping one variable (e.g. `player_credibility: low → high`) and re-running only steps 8–9 (policy + response). This reuses expensive upstream labelling and cheaply multiplies training density on decision-critical scenarios.

### Stage 6–7: Validation, Packaging, Splitting
A rule-based validator checks schema compliance, stance-delta consistency, reveal-ceiling adherence, and response length. Valid turns are packed into three aligned JSONL artifacts: *full trace*, *head-supervision* (context + all labels), and *SFT* (context + latent state + target response). A deterministic 80/10/10 split is made **by episode**, not by turn, preventing data leakage across splits.

## Part 2 — Training Pipeline

### Latent State Schema Z_t

Every turn is annotated with six structured components:

| Symbol | Group | Fields |
|--------|-------|--------|
| **C_t** | Interpretation | `dialogue_act` (multi-label, 10 classes), `tone` (6), `risk_type` (5) |
| **A_t** | Affect / Appraisal | `valence`, `arousal`, `threat`, `control` (3 levels each) |
| **M_t** | Player Model (ToM) | `player_intent` (9), `player_knowledge` (4), `player_credibility` (3) |
| **R_t** | Relational Stance | 6 dimensions (affection, respect, dominance, familiarity, trust, obligation) × level (VL/L/N/H/VH) + delta direction |
| **N_t** | Norm Constraints | `duty_pressure`, `secrecy_pressure`, `face_pressure`, `value_conflict` |
| **D_t** | Response Policy | `response_policy` (10), `reveal_decision` (4), `repair_strategy` (5) |

In total there are **29 classification targets** per turn.

### Model Architecture: Shared Backbone + Classification Heads

```
[tokenised context] → Qwen3-4B (QLoRA, 4-bit) → last-token pooled hidden state (h)
                                                             ↓
                          ┌──────────────────────────────────┴──────────────────────────────────┐
                    C_t heads (×3)          A_t + M_t heads (×7)          R_t + N_t + D_t heads (×19)
                          └──────────────────────────────────┬──────────────────────────────────┘
                                                     LM head (response generation)
```

Each classification head is a 2-layer MLP: `hidden_size → 256 → n_classes`. QLoRA (rank 16–32) keeps the 4B-parameter backbone trainable within a 12 GB VRAM budget.

### Stage 1 — Latent Predictor
Train all 29 heads jointly on the *head-supervision* artifact using a weighted multi-head loss:

```
L = λ_C·L_C + λ_A·L_A + λ_M·L_M + λ_R·L_R + λ_N·L_N + λ_D·L_D
```

Weights upweight R_t and D_t (λ=2.0) because they directly drive NPC behaviour. Key eval targets: response-policy F1 ≥ 0.75, secret-leakage rate ≤ 0.05.

### Stage 2 — Response Generator (SFT)
Train the LM head on the *SFT* artifact: given dialogue context **plus gold latent state**, predict the NPC response. Run first with gold labels (ceiling), then with Stage 1 predictions (deployment realism). The gap between the two is a key result.

### Stage 3 — Joint Multi-Task Fine-Tuning
Both objectives are trained simultaneously:

```
L_joint = L_latent_heads + λ_Y · L_response_NLL + λ_consistency · L_consistency
```

`L_consistency` penalises responses that leak secrets when `reveal_decision = none`, implementing a rule-based reward signal. Joint training closes the gold-vs-predicted latency gap identified in Stage 2.

### Stage 4 — Selective Router (planned)
A lightweight binary classifier on top of D_t/N_t hidden states decides whether to invoke a slower reflective path. Triggers on high-stakes states: `value_conflict = strong`, `secrecy_pressure = high AND player_knowledge = informed`, or consecutive trust drops.

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Structured latent state over implicit reasoning | Enables auditable NPC behaviour (e.g. secret-keeping can be tested directly) |
| Teacher-generated labels, not human annotation | 100× cheaper; teacher sees the same scene context as the student model |
| Counterfactual augmentation | Cheaply generates hard decision-boundary examples without full re-generation |
| Episode-level train/val/test split | Prevents a model from seeing earlier turns of a test-set conversation during training |
| QLoRA 4-bit on Qwen3-4B | Fits in 12 GB VRAM; LoRA adapters are parameter-efficient for fine-tuning |
| Weighted multi-head loss | Lets R_t and D_t dominate without starving semantically weaker heads |
