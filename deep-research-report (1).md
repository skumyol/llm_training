# Assessment of the llm_training codebase

## Executive judgment

This codebase is not a toy scaffold. It already embodies a serious research thesis: decompose NPC dialogue into an explicit structured social state, supervise that state with 29 labels, and then generate responses conditioned on it. The repository also contains a second, smaller-model track for ablations and efficiency work, which is exactly the kind of dual-track design that can support a publishable paper if the empirical story is tightened. In other words, the project already has a credible *research shape*. The main repository exposes a full LLM path with staged training and a separate SLM benchmark path with GRU, AWD-LSTM, GPT, PrefixGPT, MoE, and Mamba-like variants. citeturn46view0

My central conclusion is that the highest-return improvements are **not** primarily about swapping in a completely different backbone. Your biggest bottlenecks are instead: a conditioning mismatch in the SLM benchmark path, an underpowered joint-training objective for a 29-head multitask problem, and an evaluation stack that still under-measures whether the hidden state actually contains the social reasoning you care about. If you fix those three things, the paper becomes materially stronger; if you only change architectures, you are likely to get noisier experiments without resolving the core scientific weakness. citeturn33view1turn35view4turn36view0turn39view1

There is also good news. Several issues that would have been serious paper blockers appear to have been addressed in the checked-in code: `JointDataset` now verifies `episode_id` and `turn_idx` alignment instead of blindly zipping files; the validator now checks secret leakage via both `secret_id` matches and scenario-defined leakage keywords; and the counterfactual augmenter no longer applies a single midpoint value uniformly across an entire episode. Those are all meaningful improvements to data integrity. citeturn8view1turn16view0turn16view1turn13view0turn14view0

## What the codebase already gets right

The strongest part of the project is the **factorization itself**. The repository makes the modeling assumption explicit: first infer structured social state, then generate dialogue conditioned on that state. That is far more defensible for controllable NPC dialogue than an undifferentiated next-token baseline, because it gives you hooks for analysis, safety checks, and ablations. The README makes clear that the system is organized around a latent predictor and a response generator, and the code backs this up with dedicated training, evaluation, packaging, and inference paths. citeturn46view0turn24view5

The LLM training stack is also better engineered than many academic repositories. The latent predictor supports multiple pooling strategies, weighted multi-head supervision, checkpointing, MLflow logging, and evaluation bundles. The codebase already logs per-run metrics and saves structured artifacts, which is extremely important for paper-quality ablations. citeturn28view4turn28view5turn24view5

The current evaluation artifacts show that the system is doing something nontrivial rather than merely memorizing obvious cues. Some heads are already reasonably strong, including `risk_type` at about 0.892 accuracy, `face_pressure` at about 0.868, and `arousal` at about 0.854, while secret leakage is reported at 0.0 in both latent and response evaluation files. That means the pipeline is not fundamentally broken. At the same time, the weaker heads are exactly the ones that matter most for believable social interaction: `familiarity_delta` is about 0.499, `dominance_delta` about 0.572, `repair_strategy` about 0.593, `secrecy_pressure` about 0.638, and `response_policy_f1` about 0.512. That pattern is diagnostically useful: the codebase is better at local classification than at long-horizon social dynamics and policy control. citeturn41view0turn42view0

## The highest-value technical gaps

The single most important architectural problem is a **conditioning disconnect** on the SLM side. In the benchmark architecture file, `PrefixTinyGPTLM` is explicitly parameterized with `cond_dim=8`, meant to represent OCEAN plus VAD. However, the benchmark runner builds a tokenizer from GPT-2 tokenization or a char fallback, then supplies conditioning vectors through an optional external embedding extractor; if that extractor is absent, the conditioning vector is just zeros. In other words, the from-scratch small-LM benchmark is not consistently testing the research hypothesis “personality and affect conditioning improves dialogue.” It is often testing either semantic side-information or no conditioning at all. That is a major experimental confound. citeturn33view1turn35view4turn35view5turn46view0

A second, subtler issue is that the prefix-conditioning implementation is **soft-prefix at the input embedding level**, not a true per-layer key/value prefix mechanism. The code comment is actually candid about this: it describes the module as a “portable” scaffold that keeps the conditioning interface but prepends learned prefix embeddings to the input stream rather than implementing true KV-prefix injection. That is perfectly reasonable engineering, but the paper must describe it accurately. If the manuscript overclaims “deep prefix” or “per-layer prefix conditioning,” reviewers will catch the mismatch. citeturn29view0turn30view4turn43search0

The third major gap is in **joint optimization**. The current `ConsistencyLoss` is simple: it penalizes the product of `P(reveal=full)` and `P(secrecy=high)`, and the total objective uses a fixed `lambda_consistency` without a warmup schedule or adaptive balancing. For a model that predicts 29 structured targets plus language generation, that is too weak and too static. The literature on multitask learning has shown repeatedly that fixed manual loss weights are often suboptimal, and methods such as GradNorm or uncertainty-based weighting improve training stability and task balance. Your current loss is directionally sensible, but it is not rich enough for the task decomposition you have designed. citeturn26view2turn26view4turn24view3turn43search2turn43search3

The fourth issue is that **counterfactual generation is improved but still not fully sequential**. The current augmenter now flips values per turn and relabels the turn, which fixes the earlier “single midpoint for all turns” corruption. But it still calls the labeler with the original `dialogue_history`, and it sets `prior_R_t` from the copied turn rather than from the newly generated prior counterfactual turn. That means later turns in a counterfactual episode are not fully conditioned on earlier counterfactual responses and stance updates. The result is better than before, but still not a truly coherent alternate trajectory. citeturn13view0turn14view0

## The architecture changes I would actually make

I would **not** spend your next cycle replacing the main LLM backbone. The repository already supports a strong parameter-efficient adaptation pattern: continuous-prefix conditioning and LoRA-style low-rank adaptation are both literature-backed, efficient, and appropriate for a structured-control setting. Prefix-style prompting is a defensible approach for conditioning generation, and LoRA is a well-established way to adapt large causal LMs with far fewer trainable parameters and lower memory cost. The architectural leverage is there already; the issue is how much information you put into the conditioning channel and how faithfully you train it. citeturn43search0turn43search1turn46view0

The code change with the highest expected payoff is to **expand the conditioning vector from static OCEAN+VAD into a hybrid static-plus-dynamic control vector**. Concretely, I would keep the 8 static dimensions, then append compact dynamic variables derived from the latent state—especially selected `R_t` deltas and `D_t` policy variables—and add a tiny history encoder over the last few turns. This is exactly aligned with your own recommendation list, and it is the correct direction. Right now the benchmark PrefixGPT fixes `cond_dim=8`; that is too restrictive for a task whose difficulty lies in dynamic social updates, not just static persona. My recommendation is to run a clean ablation at 8D, 16D, and 32D with the same model size and data split. citeturn33view1turn30view4turn46view0

For the SLM paper track, the best near-term primary model is **still PrefixGPT**, but only after you fix the conditioning path. It gives you the cleanest causal story: explicit low-dimensional control vector, transparent prefix projection, and a straightforward ablation axis. I would keep **Mamba-like** as a secondary architecture for efficiency experiments, especially if you later care about longer conversational histories, because selective state-space models are attractive for linear-time sequence scaling. But I would not make Mamba-like the flagship model for this submission cycle. The reason is simple: your task is heavily about discrete, content-based social reasoning, and even the Mamba paper frames selectivity as the key step needed to make SSMs competitive on such data. Your current Mamba-like implementation is a simplified benchmark variant, not the place to anchor the paper’s strongest claim. citeturn45search1turn46view0turn33view3

I would treat **MoE as exploratory only**, not submission-critical, unless you also add routing diagnostics. Sparse expert models can be very strong, but the MoE literature is explicit that routing instability and load balancing are central engineering problems. The repository already includes a MoE path, but your paper will not benefit from it unless you report routing entropy, expert utilization, and collapse behavior. Otherwise MoE just increases the complexity of the story without clarifying the science. citeturn45search0turn33view3

Finally, I strongly recommend **teacher-to-student distillation from the LLM path into the SLM path**. Distillation is one of the most robust ways to compress useful hidden structure into smaller models, and there is ample evidence from DistilBERT, MiniLM, and generation-oriented teacher-student work that a student can preserve a large fraction of a teacher’s competence when supervised on logits and internal representations, not only hard labels. In your setting, the natural recipe is a mixture of KL on response logits, KL or CE on latent-head outputs, and MSE on selected hidden representations. This is far more likely to improve SLM controllability than a blind architecture search. citeturn44search0turn44search2turn44search12

## The evaluation changes required for a publishable paper

Your current evaluation stack is **good but not yet publication-hard**. On the SLM side, the training loop optimizes on validation loss and perplexity, and the eval script adds BLEU and Distinct. Those are useful, but they do not directly answer the scientific question you want the paper to answer: *does the model encode and preserve the intended social state?* Right now, a fluent model can still score well while failing on stance tracking or policy adherence. citeturn36view0turn39view1turn39view2

The single most important addition is a **standalone social-state probing benchmark**. Freeze the SLM hidden states and train simple linear probes to predict the same 29 labels you already supervise on the LLM path. This is methodologically clean, cheap to run, and scientifically valuable: it lets you compare whether the social variables are linearly recoverable from each architecture, independent of token-level fluency. Probing work in representation analysis has long used exactly this logic to localize what linguistic or semantic information is present in hidden states. For your paper, that would turn the claim “the SLM learned social reasoning” from an intuition into a measurable statement. citeturn44search3turn44search7turn41view0

I would also be careful with the current reported router results. A routing F1 of 1.0, precision 1.0, and recall 1.0 on 683 evaluations, combined with a slow-path rate of roughly 0.537, is not automatically a strength. My interpretation is that the benchmark is either too easy, too aligned with the decision rule, or too conservative to demonstrate meaningful cost-quality tradeoffs. I would not foreground those numbers in a paper until you verify there is no label leakage and create an adversarial or out-of-family split. citeturn42view1

The response metrics also need a more careful narrative. A ROUGE-L of about 0.098 with zero measured contradiction and zero measured leakage suggests a system that is relatively safe by its own metrics, but not yet strongly reference-matching. That is not necessarily fatal for dialogue, because multi-reference ambiguity is real, but it means ROUGE should remain secondary. For the paper, I would center the evaluation on policy adherence, stance consistency, secret-keeping, and blinded human preference for character believability, while using ROUGE and BLEU only as supporting diagnostics. citeturn42view0turn39view0turn39view1

## What I would prioritize before submission

If I had to compress this into a strict priority order, I would do five things.

**First, unify the conditioning story.** Make the SLM benchmark actually consume the intended control variables rather than optional semantic embeddings or zeros, and state clearly whether the conditioning is static, dynamic, or hybrid. This is the highest-impact fix because it affects the validity of your core ablations. citeturn33view1turn35view4turn46view0

**Second, strengthen multitask training.** Replace the fixed `lambda_consistency` regime with either a warmup schedule plus GradNorm, or a warmup schedule plus uncertainty-weighted loss balancing. Also expand consistency regularization beyond the single secrecy–reveal interaction to include policy–norm compatibility and stance-transition constraints. citeturn26view2turn26view4turn43search2turn43search3

**Third, rebuild the SLM tokenizer around the actual domain.** The current runner uses GPT-2 tokenization or a char fallback. For a compact dialogue model, a domain-tuned tokenizer in the 15k–20k range is a much better fit than a generic 50k vocabulary. The code already passes `vocab_size` from the tokenizer into the model, so the plumbing is there; you mainly need a better tokenizer build step and a reproducible training corpus. citeturn35view5turn33view3

**Fourth, add LLM-to-SLM distillation.** This is the most principled way to transfer the latent-state competence you are already acquiring on the LLM side into the faster models you want for deployment or interactive use. citeturn44search0turn44search2turn44search12

**Fifth, add probe-based evaluation and a harder routing benchmark.** Without these, the submission risks looking like an interesting engineering system with insufficiently discriminative evidence for the central claim. citeturn44search3turn44search7turn42view1

## Open questions and limitations

I did not execute the training code end-to-end, so this assessment is based on the checked-in repository structure, source files, and committed evaluation artifacts rather than a live reproduction of results. That means I am most confident about structural findings and code-path mismatches, and somewhat less confident about runtime-only issues such as device placement corner cases or data-loader performance pathologies. citeturn46view0turn24view5turn36view0

The most important unresolved question is whether you want the paper to make its strongest claim about **controllability**, **efficiency**, or **human-perceived believability**. The current codebase is closest to a strong controllability paper. It can become an efficiency paper after distillation and tokenizer compression. It can become a believability paper only if you invest in a real human study. The architecture work I recommended is compatible with all three, but the evaluation emphasis should be chosen deliberately. citeturn46view0turn39view1turn42view0

My final verdict is straightforward: **the best path forward is to improve conditioning fidelity, multitask optimization, and hidden-state evaluation before chasing a new backbone**. If you do that, the repository can support a paper with a coherent scientific contribution. If you do not, a new architecture will mostly rearrange variance rather than solve the main problem. citeturn33view1turn26view4turn36view0turn41view0
